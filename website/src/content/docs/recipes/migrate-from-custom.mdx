import { Aside } from '@astrojs/starlight/components';

This guide is for developers who built their own NestJS + Inertia.js integration — a `src/inertia/` folder with a service, middleware, module, shell renderer, and SSR loader — and want to replace it with `@dudousxd/nestjs-inertia`.

By the end you will have: fewer files to maintain, auto-codegen for typed pages and routes, a typed `<Link>` component, CSRF handled by the lib, and SSR wired via config rather than a bespoke service.

This guide is based on a real migration of a production app (navy-nestjs / squid-nestjs). The before-state files at `src/inertia/` are referenced directly so the examples reflect real code, not invented stubs.

---

## 1. Audit your current code

Before touching a single file, inventory everything inside your `src/inertia/` directory and classify each item. Hand-rolled integrations converge on roughly the same shape. Here is the canonical file list and where each file ends up after the migration.

### Files replaced by the lib (delete after migration)

| File | What it does | Replaced by |
|---|---|---|
| `inertia.module.ts` | NestJS `@Global()` module, registers providers, wires middleware via `configure()` | `InertiaModule.forRoot(...)` auto-wires everything |
| `inertia.service.ts` | `render()` / `redirect()` / `location()` per-request service, attached to `req.inertia` | Lib's `InertiaService` — same API, attached identically |
| `inertia.middleware.ts` | Constructs `InertiaService`, patches `suppressPostSendWrites` on the response | `InertiaMiddleware` in the lib, auto-registered |
| `inertia.types.ts` | `PageObject`, `SsrResult`, `SharedFactory`, `Express.Request` augmentation | Re-exported from `@dudousxd/nestjs-inertia` |
| `inertia.tokens.ts` | `INERTIA_ASSET_VERSION`, `INERTIA_MANIFEST` DI tokens | Replaced by `INERTIA_MODULE_OPTIONS` (single token) |
| `asset-version.provider.ts` | Reads Vite manifest, computes SHA-1 hash, falls back to UUID in dev | Pass a `version` factory to `forRoot` — same logic, you own it |
| `shell.ts` | HTML shell renderer: injects page JSON, SSR head/body, Vite HMR scripts | Pass a `rootView` function to `forRoot` — same logic, you own it |
| `ssr-loader.service.ts` | Lazily imports the SSR bundle, caches it, swallows load errors in dev | Pass `ssr.bundlePath` to `forRoot` |

### Files to keep (move out of `src/inertia/` before deleting the folder)

| File | What it does | Where it goes |
|---|---|---|
| `inertia-auth.guard.ts` | Checks `req.user`, throws `UnauthorizedException` | `src/auth/` — auth is an app concern, not a lib concern |
| `inertia-auth.guard.spec.ts` | Unit tests for the guard | `src/auth/` alongside the guard |
| `squid-inertia.middleware.ts` (or equivalent) | Shares `auth` payload via `req.inertia.share(...)` | `src/common/middleware/` |
| `squid-inertia.middleware.spec.ts` | Tests for the shared-props middleware | `src/common/middleware/` |
| `inertia-not-found.filter.ts`, `inertia-forbidden.filter.ts` | HTTP exception filters that render Inertia pages | `src/common/exceptions/` or `src/filters/` |

After completing this audit you should know exactly which files you are deleting and which you are moving.

## 3. Move app-specific code out of `src/inertia/`

Do this step **before** deleting anything. Use `git mv` so history is preserved and `git blame` still works after the migration.

```bash
# Auth guard — lives with auth concerns, not Inertia concerns
git mv src/inertia/inertia-auth.guard.ts      src/auth/inertia-auth.guard.ts
git mv src/inertia/inertia-auth.guard.spec.ts src/auth/inertia-auth.guard.spec.ts

# App-level shared-props middleware
git mv src/inertia/squid-inertia.middleware.ts      \
       src/common/middleware/squid-inertia.middleware.ts
git mv src/inertia/squid-inertia.middleware.spec.ts \
       src/common/middleware/squid-inertia.middleware.spec.ts

# Exception filters (if you have them)
git mv src/inertia/inertia-not-found.filter.ts \
       src/common/exceptions/inertia-not-found.filter.ts
```

After moving the files, update every caller. The import paths are the only change — the implementations are untouched:

```ts
// Before (every controller that uses the guard)
import { InertiaAuthGuard } from '@/inertia/inertia-auth.guard';

// After
import { InertiaAuthGuard } from '@/auth/inertia-auth.guard';
```

Find all callers in one shot:

```bash
grep -rn "from.*inertia/inertia-auth.guard"   src/ --include="*.ts"
grep -rn "from.*inertia/squid-inertia"         src/ --include="*.ts"
grep -rn "from.*inertia/inertia-not-found"     src/ --include="*.ts"
```

<Aside type="caution">
If your old `InertiaModule` **exported** the auth guard or shared-props middleware (so downstream modules could import them), those downstream modules now need to import from the new path. Update their `imports` arrays and remove the re-exports from `inertia.module.ts`.
</Aside>

**Verify:** `pnpm exec tsc --noEmit` — TypeScript should still pass (it will error on missing `./inertia/inertia.module` imports, but those are in `app.module.ts` which you fix next).

## 4. Configure `InertiaModule.forRoot(...)` in `app.module.ts`

This is the core of the migration. A single `InertiaModule.forRoot(...)` call replaces the old bare `InertiaModule` import and brings with it: the service, the middleware, the shell renderer, the SSR loader, and the asset-version provider.

### The `version` option — replaces `asset-version.provider.ts`

Your custom `assetVersionProvider` read the Vite manifest and computed a SHA-1 hash. The lib does **not** auto-discover the manifest — you pass the result as the `version` option. Copy your existing hash logic into a standalone function:

```ts
// src/app.module.ts (top of file, before @Module)
import { createHash, randomUUID } from 'node:crypto';
import { readFileSync } from 'node:fs';
import { resolve } from 'node:path';

function computeAssetVersion(): string {
  try {
    const path = resolve(
      process.cwd(),
      'dist/inertia/client/.vite/manifest.json',
    );
    const manifest = JSON.parse(readFileSync(path, 'utf8')) as Record<string, unknown>;
    return createHash('sha1')
      .update(JSON.stringify(manifest))
      .digest('hex')
      .slice(0, 32);
  } catch {
    // Dev: no manifest yet — return a fresh UUID each restart so the
    // client always detects a version change and reloads.
    return randomUUID().replace(/-/g, '');
  }
}
```

Pass it to `forRoot` as a factory reference (not a call): `version: computeAssetVersion`. The lib calls it once at module init time.

### The `rootView` option — replaces `shell.ts`

Your `shell.ts` rendered an HTML document string with the Inertia page JSON, SSR head/body, and Vite HMR scripts. Migrate that logic verbatim into the `rootView` function:

```ts
rootView: (ctx) => {
  const { page, ssr, manifest, assetVersion: _assetVersion } = ctx;

  function escapeHtml(s: string): string {
    return s
      .replace(/&/g, '&amp;')
      .replace(/</g, '&lt;')
      .replace(/>/g, '&gt;')
      .replace(/"/g, '&quot;')
      .replace(/'/g, '&#39;');
  }

  const pageJson = escapeHtml(JSON.stringify(page));
  const head = ssr?.head.join('\n') ?? '';
  const body = ssr?.body ?? '';

  const m = manifest as Record<string, { file: string; css?: string[] }> | null;
  const entry = m?.['app/client.tsx'];
  const jsHref = entry ? `/${entry.file}` : '/app/client.tsx';
  const cssHref = entry?.css?.[0] ? `/${entry.css[0]}` : null;

  // Dev only: inject Vite HMR client + React refresh preamble.
  // In prod `entry` is defined (manifest is present), so these are empty strings.
  const viteHmrScript = entry
    ? ''
    : `<script type="module" src="/@vite/client"></script>`;
  const reactRefreshPreamble = entry
    ? ''
    : `<script type="module">
import RefreshRuntime from "/@react-refresh"
RefreshRuntime.injectIntoGlobalHook(window)
window.$RefreshReg$ = () => {}
window.$RefreshSig$ = () => (type) => type
window.__vite_plugin_react_preamble_installed__ = true
</script>`;

  // SSR: createInertiaApp returns the full <div id="app"> wrapper.
  // CSR: emit the empty mount point for client hydration.
  const appDiv = ssr
    ? body
    : `<div id="app" data-page="${pageJson}"></div>`;

  return `<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <link rel="icon" type="image/svg+xml" href="/favicon.svg" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>My App</title>
    ${head}
    ${cssHref ? `<link rel="stylesheet" href="${cssHref}" />` : ''}
    ${viteHmrScript}
    ${reactRefreshPreamble}
  </head>
  <body>
    ${appDiv}
    <script type="module" src="${jsHref}"></script>
  </body>
</html>`;
},
```

<Aside type="tip">
If your shell is a plain static file with no dynamic logic, you can pass a file path string instead of a function: `rootView: 'dist/inertia/root.html'`. The lib reads and serves the file directly. For dev/prod branching (conditional HMR scripts), the function form is required.
</Aside>

### The `ssr` option — replaces `ssr-loader.service.ts`

```ts
ssr: {
  enabled: process.env.NODE_ENV === 'production',
  bundlePath: resolve(process.cwd(), 'dist/inertia/ssr/ssr.mjs'),
  throwOnError: false, // true = crash on missing bundle; false = fall back to CSR silently
},
```

The `bundlePath` **must be absolute**. A relative path resolves from inside `node_modules`, not from `process.cwd()`, and fails silently in production.

### The `share` option — replaces simple shared-props middleware

For straightforward shared-props cases (e.g. injecting the current user), you can skip the middleware entirely and use the `share` option:

```ts
share: async (req) => ({
  auth: await buildAuthPayload((req as any).user),
}),
```

Keep the middleware form when your shared-props logic requires DI, complex async operations, or side effects that don't fit cleanly in a plain function.

### The `codegen` option

```ts
codegen: {
  enabled: process.env.NODE_ENV !== 'production',
},
```

In dev this starts the file watcher automatically when NestJS boots (`nest start --watch`). In production the watcher is skipped. CI should run `pnpm exec nestjs-inertia codegen` explicitly before the build step.

### The `csrf` option

If your custom implementation had a hand-rolled CSRF cookie:

```ts
csrf: {
  secret: process.env.CSRF_SECRET ?? 'change-me-in-production',
  cookieName: 'XSRF-TOKEN',
  tokenContext: 'session', // ties the CSRF token to the session — rotates on login/logout
},
```

### Complete `forRoot` call (sync)

```ts
import { createHash, randomUUID } from 'node:crypto';
import { readFileSync } from 'node:fs';
import { resolve } from 'node:path';
import { InertiaModule } from '@dudousxd/nestjs-inertia';

function computeAssetVersion(): string {
  try {
    const raw = readFileSync(
      resolve(process.cwd(), 'dist/inertia/client/.vite/manifest.json'),
      'utf8',
    );
    const manifest = JSON.parse(raw) as Record<string, unknown>;
    return createHash('sha1')
      .update(JSON.stringify(manifest))
      .digest('hex')
      .slice(0, 32);
  } catch {
    return randomUUID().replace(/-/g, '');
  }
}

@Module({
  imports: [
    InertiaModule.forRoot({
      version: computeAssetVersion,
      rootView: (ctx) => { /* ... your shell logic ... */ },
      ssr: {
        enabled: process.env.NODE_ENV === 'production',
        bundlePath: resolve(process.cwd(), 'dist/inertia/ssr/ssr.mjs'),
      },
      codegen: { enabled: process.env.NODE_ENV !== 'production' },
    }),
  ],
})
export class AppModule {}
```

### Async variant (`forRootAsync`)

If your version or SSR config depends on async DI values (e.g. a config service):

```ts
InertiaModule.forRootAsync({
  imports: [ConfigModule],
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    version: computeAssetVersion,
    rootView: 'dist/inertia/root.html',
    ssr: {
      enabled: config.get('NODE_ENV') === 'production',
      bundlePath: resolve(process.cwd(), config.get('SSR_BUNDLE_PATH')),
    },
  }),
}),
```

## 5. Replace `InertiaService` usage in controllers

Every controller that imported `InertiaService` from `@/inertia/inertia.service` now imports it from the library. The API is intentionally identical — `render()`, `redirect()`, and `location()` have the same signatures.

**Before (every Inertia controller):**

```ts
import { InertiaService } from '@/inertia/inertia.service';
```

**After:**

```ts
import type { InertiaService } from '@dudousxd/nestjs-inertia';
```

Find all files to update:

```bash
grep -rn "from.*inertia/inertia.service" src/ --include="*.ts"
```

If you also imported `PageObject`, `SsrResult`, or `SharedFactory` types from the old path, those are re-exported from the lib:

```ts
// Before
import type { PageObject, SsrResult, SharedFactory } from '@/inertia/inertia.types';

// After
import type { PageObject, SsrResult, SharedFactory } from '@dudousxd/nestjs-inertia';
```

### API comparison

| Method | Custom impl | Lib | Notes |
|---|---|---|---|
| `req.inertia.render(component, props)` | `async render(component: string, props?: Record<string, unknown>): Promise<void>` | Same | No change |
| `req.inertia.share(input)` | `share(input: SharedInput): this` — `SharedInput` = plain object or `() => Promise<Record>` | Same — factory also receives `(req: Request)` as first arg | JS ignores extra args, no runtime break |
| `req.inertia.redirect(url)` | Custom (if present) | `redirect(url: string, status?: number): void` | Verify status defaults match |
| `req.inertia.location(url)` | Custom (if present) | `location(url: string): void` | Identical |

In the real navy migration, none of the 20+ controllers required any signature changes — only the import path was updated.

## 6. Move app-specific code out of `src/inertia/`

You already moved the files in step 3 (before any deletions). Now update the remaining cross-references. The two things that typically need updating:

### Re-register the shared-props middleware in `app.module.ts`

After moving `squid-inertia.middleware.ts` to `src/common/middleware/`, wire it in `app.module.ts`. Register it **after** the middleware that populates `req.user` — otherwise `req.user` will be `undefined` when the shared factory runs.

```ts
// src/app.module.ts
import { SquidInertiaMiddleware } from './common/middleware/squid-inertia.middleware';

@Module({
  providers: [SquidInertiaMiddleware],   // <-- also add as a provider
})
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(cookieParser()).forRoutes('{*splat}');
    consumer.apply(UserMiddleware).forRoutes('{*splat}');          // populates req.user
    consumer.apply(ImpersonationMiddleware).forRoutes('{*splat}'); // modifies req.user
    consumer.apply(SquidInertiaMiddleware).forRoutes('{*splat}');  // reads req.user
    // DO NOT add InertiaMiddleware here — forRoot auto-registers it
  }
}
```

### Update the auth guard import in controllers

If you grep revealed controllers still importing from `@/inertia/inertia-auth.guard`, those controllers also need the import updated (you may have missed some in step 3):

```bash
# Confirm nothing still points at the old path
grep -rn "from.*inertia/inertia-auth.guard" src/ --include="*.ts"
# Should return nothing
```

Here is the complete before/after for the navy migration. Your module will look different but the structural changes are identical.

import { InertiaModule } from '@dudousxd/nestjs-inertia';  // <-- lib

@Module({

      ssr: {
        enabled: process.env.NODE_ENV === 'production',
        bundlePath: resolve(process.cwd(), 'dist/inertia/ssr/ssr.mjs'),
      },
      codegen: { enabled: false }, // enable in dev if you want auto-watch

    ProfileModule,
    AuthModule,

  providers: [

    SquidInertiaMiddleware,  // <-- must be a provider for DI to resolve it

## 9. Set up codegen

Codegen generates typed page maps, route constants, and an `api.*` surface from your controller decorators. It runs once at startup and re-runs on every file change in `nest start --watch`.

### Initialize

```bash
pnpm exec nestjs-inertia init
```

This creates:
- `nestjs-inertia.config.ts` — codegen configuration (pages glob, output dir, etc.)
- `nestjs-inertia.d.ts` — TypeScript ambient module declaration
- Adds `.nestjs-inertia/` to `.gitignore`

### What gets generated

When the app starts (or when `nestjs-inertia codegen` is run explicitly), the following files are emitted into `.nestjs-inertia/`:

```
.nestjs-inertia/
  pages.ts       ← typed page component map (Page.Dashboard, Page.Profile, …)
  routes.ts      ← Route.* and Path.* typed route constants
  api.ts         ← @ApplyContract endpoints as a typed client surface
```

### Auto-watch in development

Enable the watcher in `forRoot`:

```ts
codegen: { enabled: process.env.NODE_ENV !== 'production' }
```

Then run `nest start --watch` as normal. The watcher fires whenever you add, rename, or delete a controller. No separate process needed.

### CI

In CI or Docker builds, run codegen explicitly before the TypeScript compilation step:

```bash
pnpm exec nestjs-inertia codegen
pnpm exec tsc --noEmit
pnpm run build
```

## 11. Common gotchas

### `SharedFactory` signature

Your custom `SharedFactory` type was `() => Promise<Record<string, unknown>>` — a zero-argument factory that closed over `req`. The lib's factory receives `(req: Request)` as its first argument:

```ts
// Old shape — closure over req
req.inertia.share(async () => ({
  auth: await buildAuthPayload(req.user),
}));

// New shape — request passed explicitly
req.inertia.share(async (req) => ({
  auth: await buildAuthPayload(req.user),
}));
```

**At runtime, old zero-argument factories continue to work** — JavaScript silently ignores extra arguments. TypeScript will emit a type error about the signature mismatch. Fix it by adding the `req` parameter to your factory. In the navy migration this was a zero-line runtime change and a one-line TypeScript fix per factory.

### Auto-registered middleware — do not double-register

`InertiaModule.forRoot` automatically registers two middleware globally:

- **`InertiaMiddleware`** — attaches `req.inertia` and patches `suppressPostSendWrites`
- **`MethodSpoofMiddleware`** — translates `_method` override headers for HTML form submissions

If your old `InertiaModule.configure()` registered these manually, the lib now does it. Remove your manual registrations from `AppModule.configure()`. Registering the same middleware twice attaches `req.inertia` twice and applies the response patch twice, which can produce subtle double-write bugs.

```ts
// WRONG after migration — InertiaMiddleware is already registered by forRoot
configure(consumer: MiddlewareConsumer) {
  consumer.apply(InertiaMiddleware).forRoutes('{*splat}');  // <-- remove this
  consumer.apply(SquidInertiaMiddleware).forRoutes('{*splat}'); // keep this
}
```

### Token consolidation

Hand-rolled setups typically expose multiple DI tokens:

```ts
// Old tokens — found in inertia.tokens.ts
export const INERTIA_ASSET_VERSION = Symbol('INERTIA_ASSET_VERSION');
export const INERTIA_MANIFEST      = Symbol('INERTIA_MANIFEST');
```

The lib uses a single `INERTIA_MODULE_OPTIONS` token. If any of your providers used `@Inject(INERTIA_ASSET_VERSION)` or `@Inject(INERTIA_MANIFEST)`, refactor those providers. Options:

1. **Simplest:** pass the value directly to the provider via factory — `useFactory: () => computeAssetVersion()`. No token dependency at all.
2. **If you need the full options object:** inject `INERTIA_MODULE_OPTIONS` from `@dudousxd/nestjs-inertia` and read the `version` field.

In the navy migration, no providers outside `src/inertia/` injected these tokens — the token files were only used internally. The delete was clean.

### Inertia protocol version

The lib targets **Inertia v3** (the current major). If your app uses `@inertiajs/react@^1` or `@inertiajs/react@^2`, update your frontend dependencies first:

```bash
pnpm add @inertiajs/react@latest
```

v3 introduces `application/json` script-tag page data, nested partial reload markers, and deferred prop streaming. The server-side protocol change is handled entirely by the lib — your page components do not need to change for basic usage.

### CSRF defaults

If you add the `csrf` option, note that `secure: true` is the default in production (`NODE_ENV === 'production'`). In local development over HTTP, the cookie's `secure` flag is automatically set to `false` so the browser accepts it. No action needed for dev. For production over HTTPS (which you should always be doing), `secure: true` is correct.

### `SquidInertiaMiddleware` must be in `providers`

NestJS middleware that is registered via `consumer.apply(...)` must also be listed in the module's `providers` array when it has constructor dependencies. The navy migration hit this: `SquidInertiaMiddleware` was previously exported by `InertiaModule` (which listed it as a provider). After moving to `AppModule`, it must be added to `AppModule.providers`:

```ts
@Module({
  providers: [
    SquidInertiaMiddleware,  // <-- required for DI
    { provide: APP_GUARD, useClass: ThrottlerGuard },
  ],
})
```

### Shared-props middleware order matters

The shared-props middleware reads `req.user`. Register it **after** the middleware that authenticates the user (e.g. `UserMiddleware`, `ImpersonationMiddleware`):

```ts
configure(consumer: MiddlewareConsumer) {
  consumer.apply(UserMiddleware).forRoutes('{*splat}');          // sets req.user
  consumer.apply(ImpersonationMiddleware).forRoutes('{*splat}'); // may mutate req.user
  consumer.apply(SquidInertiaMiddleware).forRoutes('{*splat}');  // reads req.user — LAST
}
```

If `SquidInertiaMiddleware` runs before `UserMiddleware`, `req.user` is `undefined` and every page renders with `auth: null`.

## 12. What you get for free now

Switching to the lib unlocks features that are impractical to maintain in a custom in-tree implementation:

- **Auto-codegen** — page map, route constants, and `api.*` surface generated on every controller save in dev; one explicit CI command before build
- **Typed `<Link route="...">` component** — import from `@dudousxd/nestjs-inertia-client/react` (or `/vue`, `/svelte`). Route names and parameter shapes come from generated types, so typos are caught at compile time
- **`@ApplyContract` + `defineContract`** — declare the exact props your Inertia page accepts on the controller and share that type with the client. Eliminates the manual `ComponentProps` dance
- **`Route.*` / `Path.*` type helpers** — typed route builders generated from your controllers. No more magic strings
- **`@As` hierarchical naming** — override the generated page name for a controller with a scoped hierarchy (e.g. `@As('Settings.Profile')`) for clean page component organization
- **`expectInertia()` testing helpers** — assert on Inertia responses in integration tests without parsing raw JSON. Replaces hand-rolled response inspection
- **CSRF with `tokenContext`** — session-bound token invalidation. Replaces hand-rolled CSRF cookie logic
- **Partial reload markers** — `Inertia.optional(value)`, `Inertia.defer(fn)`, `Inertia.merge(value)`, `Inertia.always(value)`. Fine-grained control over which props are sent on partial reloads; v3 protocol features with no extra middleware
- **Multi-app support** — `InertiaModule.forFeature(...)` lets a single NestJS process serve multiple independent Inertia frontends with separate shell renderers, version tracking, and SSR bundles
