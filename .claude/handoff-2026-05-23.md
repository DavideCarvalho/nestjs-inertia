## What's broken / incomplete

### P0: Cross-file DTO resolution
**The #1 issue.** `packages/codegen/src/discovery/contracts-fast.ts` only resolves class types declared in the **same file** as the controller. Imported DTOs (e.g., `import { BaseResponse } from '../dto/base.response'`) fall back to the class name string, which means `api.ts` doesn't get generated for those controllers.

Navy-nestjs has DTOs in separate files (standard NestJS pattern). Result: `.nestjs-inertia/api.ts` is never generated despite controllers having `@Body() body: CreateBaseDto` + return types.

**Fix approach:** Use ts-morph's `typeNode.getType().getSymbol().getDeclarations()` to follow imports and resolve the class from its declaration file. Or use `sourceFile.getImportDeclarations()` to find the import, resolve the path, add that source file to the project, and read the class from there. Limit recursion depth to avoid explosion.

## Key architecture decisions made this session
- `defineContract` has no method/path — NestJS `@Controller`+`@Get` are the routing source of truth
- `@As` works on class+method level, composes hierarchically
- Route names auto-derived from `ClassName.methodName` (strip Controller suffix, lowercase)
- Class-validator DTOs are the zero-config path; Zod `defineContract` is the explicit path
- Auth guards, not-found filters removed from lib (app concern) → recipes in docs
- Shell uses `@inertia`/`@inertiaHead`/`@vite` directives, NOT `{{page}}` placeholders
- Dual ESM+CJS via tsup (NestJS projects compile to CJS by default even with module:nodenext)
- `InertiaModule.forRoot({ rootView })` — version is optional (auto-computed from manifest)
